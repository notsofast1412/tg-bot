# Диагностика WB и конфигурации Telegram

Проверено 19.10.2026, МСК. Цель — отличить ограничение доступа от ошибки разбора цены и от проблем настройки Telegram. Запросы выполнены через штатный HTTPS-прокси среды, с проверкой TLS. Ротация IP, обход прокси, CAPTCHA и проверки браузера не выполнялись.

## Что подтверждено по WB

Обычный GET пользовательской страницы `https://www.wildberries.ru/catalog/29220564/detail.aspx` вернул **HTTP 498**, `Content-Type: text/html`, 1130 байт. Вместо карточки обнаружены ссылки на скрипты:

```text
/__wbaas/challenges/antibot/__static/v2/index-yz9dDw8g.js
/__wbaas/challenges/antibot/__static/v2/browser-check.js
```

Это конкретный признак проверки **WB WBAAS AntiBot**. Ответ не содержит данных товара, поэтому исправление JSON-полей цены не устранит эту проблему. По такому ответу нельзя определить наличие товара или его цену.

GET `https://card.wb.ru/cards/v4/detail` с `nm=29220564`, `curr=rub`, `dest=-1257786`, `appType=1` вернул **HTTP 403**, `Content-Type: text/plain`, пустое тело. Присутствовали `server: envoy` и `x-envoy-upstream-service-time`; явных признаков отказа по allowlist в ответе не было. Сами эти заголовки не доказывают источник 403. Приписывать этот отказ только WB, только сетевому прокси или недействительному токену нельзя.

Точный критерий WBAAS, вызвавший проверку (адрес выхода, тип клиента, отсутствие браузерной сессии или другое правило), снаружи не раскрывается. Проверка на другом разрешённом сервере пока не выполнялась. Увеличение частоты запросов не является исправлением.

## Дополнительная проверка Chromium

Проверен первый ответ обычной навигации Playwright + системный Chromium 154, с чистой сессией, штатным HTTPS-прокси и без stealth-настроек. Браузер завершил навигацию с `ERR_CERT_AUTHORITY_INVALID` до получения пригодного ответа карточки. Следовательно, результат HTTP-клиента нельзя автоматически переносить на успешно настроенный браузер: его проверка ещё не состоялась.

Причина TLS-ошибки установлена по журналу Chromium и сверке отпечатков. Python/HTTPX используют системный bundle `/etc/ssl/certs/ca-certificates.crt`. Сертификат `/usr/local/share/ca-certificates/environment-proxy-ca.crt` **уже присутствует** в NSS `/home/agent/.pki/nssdb` под именем `OpenAI-nebula-dns`, с доверием `C,,`. SHA-256: `C7:1B:4D:1E:9D:77:75:C5:38:C6:88:AB:10:CE:A9:CE:41:7D:73:12:E8:98:38:F9:D1:5F:F7:32:56:CD:7F:C3`. Python и Chromium получили один и тот же сертификат сайта, подписанный этим CA; проблема не в необходимости ещё одного CA.

Журнал Chromium содержит `Error initializing NSS with a persistent database (sql:/home/agent/.pki/nssdb): NSS error code: -8126`, затем `Initializing NSS without a persistent database`. Библиотека NSS расшифровывает `-8126` как `SEC_ERROR_READ_ONLY` — `security library: read-only database`. Песочница разрешает чтение `/home/agent`, но не запись туда, а Chromium открывает NSS через `NSS_InitReadWrite`. Поэтому браузер не использует уже доверенный сертификат и сообщает `ERR_CERT_AUTHORITY_INVALID`. Поведение NSS описано в [официальной документации Chromium](https://raw.githubusercontent.com/chromium/chromium/main/docs/linux/cert_management.md); выбор каталога и вызов `NSS_InitReadWrite` проверены по [исходнику Chromium](https://raw.githubusercontent.com/chromium/chromium/main/crypto/nss_util.cc).

Первоначальное предположение об отсутствии CA оказалось неверным после проверки отпечатков. Предложенный дополнительный импорт CA был отклонён автоматической проверкой безопасности как широкое изменение доверия без явного разрешения; операция не выполнялась. Повторный импорт не нужен и не предлагается. Для продолжения обычного браузерного теста требуется разрешение песочницы на запись в существующий NSS-каталог, без добавления сертификатов, смены доверия, обхода ограничений WB или отключения TLS.

Предоставленный WB_parser начинает со страницы браузера и содержит настройки маскировки автоматизации и fetch с browser credentials. Его README не доказывает работоспособность в текущей облачной среде; перенос этих приёмов для преодоления защиты противоречил бы ограничению из ТЗ «не обходить CAPTCHA, авторизацию … и другие защитные механизмы».

## Что подтверждено по настройкам Telegram

В доступной этому чату конфигурации:

- в черновике есть требование `BOT_TOKEN`, но `has_saved_binding=false`;
- `OWNER_ID` находится в `pending_runtime_requirements`;
- работающая машина сообщает `spec_revision=1` и пустые списки secret/runtime bindings;
- в процессе отсутствуют `BOT_TOKEN`, `OWNER_ID`, `NOTIFICATION_CHAT_ID`, локальный `.env` отсутствует.

Следовательно, приложению ещё не переданы значения для проверки Telegram. Это не ответ Telegram «неверный токен»: авторизованный getMe не выполнялся. Где именно пользователь сохранил токен, по этим сведениям установить нельзя; токен мог быть введён в другом месте или конфигурация могла остаться неприменённой. Наличие самого требования в черновике не означает наличие значения секрета. GitHub Secrets не передаются этой машине автоматически.

Показанный runtime allowlist также не содержит custom-доменов из черновика, а его состояние указано как `unknown`. Это дополнительное расхождение конфигураций, но оно не доказывает, что наблюдаемый 403 вызван сетевой политикой: HTML WBAAS действительно получен, ранее получен и реальный ответ Ozon.

## Изменения в приложении

Диагностика распознаёт сигнатуру WBAAS и объясняет, что вместо карточки пришла проверка доступа. Пустой HTTP 403 больше не приписывается без доказательств маркетплейсу. Явный proxy-denial отделяется от ответа площадки. В каждом случае сохраняются cooldown и последняя достоверная цена, повторный браузерный обход не запускается. Добавлены регрессионные тесты на HTTP 200/498 с WBAAS, непрозрачный 403 и явный отказ прокси.

## Что требуется извне

Для Telegram нужно сохранить привязку `BOT_TOKEN` и значение `OWNER_ID` в настройках именно этой среды, применить/опубликовать конфигурацию и заново проверить наличие переменных и getMe. Передавать секрет в чат не нужно. Сохранение и публикация выполняются через интерфейс среды, доступные агенту инструменты сохраняют только черновик.

Для WB необходим доступ к обычной карточке/цене через разрешённый источник без проверки защиты: например, согласованный доступ с площадкой или предусмотренный ею источник данных. Перенос на целевой Ubuntu-сервер можно оценить обычной диагностикой; гарантировать, что смена сервера устранит WBAAS, оснований нет. Официальный seller API также нельзя обещать как замену мониторинга произвольных чужих карточек: это другой сценарий доступа.

Для продолжения браузерного сравнения нужен описанный доступ на запись к существующему NSS. Даже после устранения TLS-ошибки доступ WB не гарантирован; это исправление доступа браузера к уже доверенным CA, а не способ преодолеть WBAAS.
