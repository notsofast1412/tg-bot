# Обслуживание и восстановление

## Обновление

1. Сделайте backup и проверьте его наличие: `sudo -u paintbot bash /opt/paintbot/scripts/backup.sh`.
2. Остановите `paintbot`: `sudo systemctl stop paintbot`.
3. От имени владельца checkout выполните `git pull --ff-only`, не теряя локальные изменения.
4. `sudo -u paintbot bash /opt/paintbot/scripts/install.sh`.
5. `sudo systemctl start paintbot`, проверьте журнал, `/status` и тестовую отправку.

Обновление не сбрасывает изменённые пороги. При изменении структуры схемы нужна
новая Alembic-миграция, а не редактирование уже применённой 0001.

## Восстановление SQLite

Остановите бот и backup timer. Сначала сохраните текущие `var/paintbot.db`,
`var/paintbot.db-wal`, `var/paintbot.db-shm` (если есть) отдельным архивом.
Не подменяйте БД у работающего процесса.

Проверьте выбранную копию:

```bash
cd /opt/paintbot
.venv/bin/python - <<'PY'
import sqlite3
with sqlite3.connect('file:var/backups/ИМЯ-КОПИИ.db?mode=ro', uri=True) as db:
    print(db.execute('PRAGMA integrity_check').fetchone()[0])
PY
```

При результате `ok` замените `var/paintbot.db` выбранной копией; старые `-wal` и
`-shm` уберите из рабочего каталога в сохранённый архив. Владелец файла должен
быть `paintbot`, права `600`. Выполните Alembic upgrade head, запустите службу и
timer. Проверьте товары, пороги, группу и `/queue`. Не удаляйте сохранённый архив
до завершения проверки. `.env` восстанавливается отдельно из защищённой копии.

Старая резервная копия не знает об отправках, сделанных после неё. При восстановлении
возможен повтор этих исторических событий: перед запуском sender проверьте
очередь и группу. Встроенная защита относится к сохранённому состоянию БД, а не
к произвольному откату времени. Для контролируемого первого запуска уберите
настройку группы в восстановленной БД через SQL/администрирование и задайте её
заново после проверки очереди.

## Диагностика

| Симптом | Проверка и действие |
|---|---|
| Нет запуска | Проверить `.env`, Python 3.12+, `.venv`, Alembic upgrade head, права на `var` |
| Конфликт polling | Остановить другие экземпляры/серверы с тем же токеном; проверить webhook |
| HTTP 403 | Площадка отказала в доступе. Проверить ту же карточку в браузере; не отключать TLS и не обходить защиту |
| HTTP 429 | Дождаться указанной паузы, уменьшить нагрузку; `/check` не снимает ограничение |
| Карточка не распознана | Прямая ссылка и точный ID; JS-only/защищённая страница может быть недоступна |
| Нет цены | Проверить статус товара: валюта, остаток, неоднозначные предложения/варианты; старая цена не считается новой |
| Не работает группа | `/setgroup`, затем `/status`; проверить отрицательный ID, членство и право отправки |
| Уведомление не пришло | Цена должна быть строго ниже порога; посмотреть `/queue`; первое событие лишь на новом переходе |
| `uncertain` | Сначала проверить группу, затем при необходимости `/retry ID` с подтверждением |
| Тайм-аут сценария | Начать добавление заново; незавершённые изменения не записываются |

Внешние журналы не должны сохранять URL Telegram с токеном. Встроенный транспорт
маскирует сетевые исключения, отладочные HTTP-логи отключены. Не включайте debug
логирование библиотек на рабочем сервере. Уведомления экранируют HTML из карточек.

Попытки проверок пишутся отдельно от изменений цен. Check logs пока не имеют
автоматической очистки: учитывайте рост (до 144 записей/товар/сутки при 10 мин),
делайте backup и при необходимости добавьте отдельную политику хранения. История
цен и очередь не очищаются автоматически, чтобы не терять аудит и состояния.

В облачной среде systemd может не быть PID 1. Там используйте прямой запуск
`cd /workspace/tgbot && .venv/bin/python -m paintbot`; production units устанавливаются
на целевом Ubuntu-сервере. Не запускайте одновременно прямой процесс и службу.
