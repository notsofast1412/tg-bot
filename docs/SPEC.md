# Техническое задание: Telegram-бот для мониторинга цен на краску

## 1. Цель проекта

Разработать полноценного Telegram-бота для автоматического мониторинга цен на товары на трёх маркетплейсах:

- Wildberries (WB);
- Ozon;
- Яндекс Маркет.

Бот должен отслеживать цены конкретных товаров, уведомлять владельца о снижении цены ниже установленного порога и сохранять историю изменения цен.

Целевая среда развёртывания — Ubuntu Server 24.04 LTS.

Бот должен работать круглосуточно как системная служба, автоматически запускаться после перезагрузки сервера и восстанавливаться после временных сбоев.

**Главный принцип:** бот отслеживает только товары, которые владелец самостоятельно добавил по прямой ссылке или артикулу. Автоматический поиск новых товаров по ключевым словам, подбор аналогов и самостоятельное добавление товаров из поисковой выдачи не нужны.

---

## 2. Способы добавления товаров

При нажатии кнопки «➕ Добавить товар» бот должен сначала уточнить у владельца способ добавления.

Показать две кнопки:

- 🔗 Добавить по ссылке
- 🔢 Добавить по артикулу

Также должна быть кнопка отмены.

### 2.1. Добавление по ссылке

1. Бот предлагает отправить одну или несколько прямых ссылок на карточки товаров.
2. Поддерживаются Wildberries, Ozon и Яндекс Маркет.
3. Можно отправлять несколько ссылок одним сообщением или несколькими сообщениями подряд.
4. Бот должен находить ссылки с протоколами `http://` и `https://`, в том числе несколько URL, написанных подряд без пробелов.
5. Для каждой ссылки бот определяет маркетплейс и пытается получить сведения о конкретной карточке товара.
6. Бот должен извлечь доступные данные:
   - название товара;
   - артикул;
   - маркетплейс;
   - актуальную цену;
   - характеристики товара;
   - цвет и объём;
   - количество единиц в упаковке, если достоверно известно;
   - прямую ссылку на карточку.
7. Если часть данных получить не удалось, бот должен сообщить об этом, не выдумывая недостающую информацию.
8. Если карточка доступна, но цена временно не получена, товар можно добавить со статусом ожидания первой успешной проверки.

Для каждого товара нужно проверять, что полученная информация относится именно к указанной карточке, а не к похожему товару или общей поисковой выдаче.

### 2.2. Добавление по артикулу

Последовательность действий:

1. Бот предлагает выбрать маркетплейс:
   - Wildberries;
   - Ozon;
   - Яндекс Маркет;
   - Отмена.
2. После выбора площадки бот просит ввести артикул.
3. Поддерживать числовые и буквенно-цифровые артикулы в соответствии с форматом выбранной площадки.
4. Бот пытается найти конкретную карточку по артикулу на выбранном маркетплейсе.
5. После получения данных бот проверяет соответствие найденного товара указанному артикулу и площадке.
6. Если товар найден, показать предварительную карточку:
   - название;
   - маркетплейс;
   - артикул;
   - актуальная цена, если доступна;
   - характеристики, цвет, объём и вариант товара, если доступны;
   - количество единиц в упаковке, если достоверно известно.
7. Владелец должен подтвердить, что найден правильный товар.
8. Если товар не найден, результат неоднозначен или данные недоступны, сообщить об этом и предложить повторить ввод либо добавить товар по ссылке.
9. Если получить карточку по артикулу не удалось, не подменять результат похожим товаром.

Один и тот же артикул на разных маркетплейсах считается разными товарами. Автоматический подбор аналогов и поиск по ключевым словам не реализовывать.

## 3. Пакетное добавление товаров

При добавлении нескольких ссылок бот должен использовать единый сценарий пакетного добавления.

Последовательность:

1. Владелец выбирает добавление по ссылке.
2. Отправляет одну или несколько ссылок.
3. Бот собирает ссылки в пакет и проверяет их.
4. Бот показывает список распознанных товаров и ошибки по отдельным ссылкам.
5. Бот запрашивает общее пользовательское название для пакета.
6. Бот предлагает выбрать один тег и порог цены для всех товаров пакета.
7. Бот показывает итоговую сводку.
8. Владелец подтверждает сохранение.

Общее название и тег применяются ко всем товарам пакета, если владелец не выбрал другой вариант в предусмотренном интерфейсе.

Каждый товар после сохранения остаётся отдельной записью со своей ценой, историей, артикулом, ссылкой, порогом и состоянием уведомления.

Обязательно реализовать:

- команду `/cancel`;
- кнопку отмены;
- тайм-аут незавершённого сценария;
- безопасное восстановление или сброс незавершённого сценария после перезапуска;
- удаление дубликатов внутри одного пакета;
- проверку дубликатов в базе;
- отображение некорректных и неподдерживаемых ссылок;
- обработку частичных ошибок;
- подтверждение перед окончательным сохранением;
- отчёт о количестве добавленных, пропущенных и ошибочных товаров.

Если цена недоступна, не придумывать её и не блокировать добавление корректной карточки, если остальные необходимые сведения получены.

## 4. Теги и пороги цен

Теги являются правилами мониторинга цены. Для каждого тега задан строгий порог срабатывания.

Все цены указываются исключительно в российских рублях (₽).

| Тег | Условие уведомления |
|---|---:|
| `#arton` | цена меньше 400 ₽ |
| `#2arton` | цена меньше 750 ₽ |
| `#6arton` | цена меньше 2 200 ₽ |
| `#belazo` | цена меньше 350 ₽ |
| `#2belazo` | цена меньше 700 ₽ |
| `#6belazo` | цена меньше 2 000 ₽ |
| `#trane` | цена меньше 350 ₽ |
| `#3trane` | цена меньше 1 000 ₽ |
| `#6trane` | цена меньше 2 000 ₽ |
| `#flame` | цена меньше 500 ₽ |
| `#molotow400` | цена меньше 5 000 ₽ |
| `#burner` | цена меньше 800 ₽ |
| `#joggle` | цена меньше 300 ₽ |
| `#2jiggle` | цена меньше 600 ₽ |

Требования:

- Сохранять написание каждого тега строго в указанном виде.
- Порог должен быть строгим: цена, равная порогу, не вызывает уведомление.
- Теги и пороги должны храниться в базе данных.
- Владелец должен иметь возможность просматривать и редактировать пороги.
- Первоначальное заполнение тегов должно быть идемпотентным: повторный запуск не создаёт дубликаты и не сбрасывает изменённые владельцем настройки.
- Изменение порога должно корректно обновлять состояние мониторинга и не создавать массовых ложных уведомлений.
- При добавлении товара владелец должен видеть выбранный тег и соответствующий порог.

Не определять количество баллонов по названию тега. Количество единиц в упаковке и объём товара нужно извлекать из подтверждённых данных карточки. Если информация неоднозначна, запросить уточнение у владельца.

## 5. Получение данных с маркетплейсов

Бот должен самостоятельно получать информацию о товарах и их актуальных ценах на Wildberries, Ozon и Яндекс Маркете.

**Не ограничивать реализацию только официальными API.** Разработчик должен самостоятельно выбрать наиболее эффективные технические способы получения информации для каждой площадки.

В зависимости от доступности и технической целесообразности допускаются:

- официальные и публичные API;
- HTTP-запросы;
- получение и разбор HTML-страниц;
- анализ структурированных данных в страницах товара;
- браузерная автоматизация;
- JavaScript-рендеринг страниц;
- другие подходящие способы извлечения информации.

Для каждого маркетплейса реализовать отдельный адаптер:

- `WildberriesAdapter`;
- `OzonAdapter`;
- `YandexMarketAdapter`.

Каждый адаптер должен предоставлять единый интерфейс получения сведений о карточке и её актуальной цене.

### Требования к получению цены

1. Получать цену именно той карточки, которую добавил владелец.
2. По возможности учитывать выбранный вариант, цвет, объём и комплектацию.
3. Проверять корректность и актуальность полученных данных.
4. Отличать фактическую цену от старой, зачёркнутой, рекомендованной или недоступной цены.
5. Не использовать рекламную цену, цену другого продавца или другого варианта товара вместо отслеживаемой цены без явно определённого правила.
6. Если маркетплейс показывает несколько цен, определить, какая из них является фактической ценой покупки для выбранного товара, либо сообщить о неоднозначности.
7. Не выдавать кэшированную цену за актуальную без соответствующей отметки.
8. При невозможности получить цену фиксировать ошибку и повторять проверку позднее.

### Резервные методы

Если основной метод перестал работать, предусмотреть возможность использовать альтернативный подход, когда он технически доступен.

Если страница не загружается, изменилась её структура, цена отсутствует или доступ ограничен, бот должен:

- зафиксировать причину ошибки;
- сохранить последнюю достоверную цену с отметкой времени;
- не считать старую цену новой;
- не отправлять ложные уведомления;
- продолжить работу с другими товарами;
- показать владельцу статус проблемы.

Не заявлять, что интеграция работает, пока её фактическая работоспособность не проверена.

Необходимо соблюдать применимые правила доступа, законодательства и ограничения частоты запросов. Не обходить CAPTCHA, авторизацию, платные ограничения и другие защитные механизмы. Если для получения данных требуется недоступное разрешение, сообщить владельцу об ограничении, не подменяя реальные данные заглушками.

## 6. Расписание проверок

Целевой интервал проверки — каждые 10 минут, если это технически возможно и допустимо для конкретного маркетплейса.

Если площадка требует более редкой проверки, использовать допустимый интервал и показывать его в статусе.

Для каждого товара хранить:

- последнюю достоверную цену;
- время последней успешной проверки;
- время последней попытки;
- время последнего изменения цены;
- результат последней проверки;
- статус мониторинга;
- состояние условия уведомления.

Отдельно вести журнал попыток проверки и историю изменения цены. Не записывать каждую проверку как изменение цены, если цена не изменилась.

### Пример расчётной нагрузки

При проверке каждые 10 минут получается до 144 циклов проверок на товар в сутки. Количество реальных HTTP-запросов зависит от реализации адаптеров и способа получения данных.

Реализовать:

- ограничение частоты запросов;
- тайм-ауты;
- ограниченные повторные попытки;
- задержки между повторами;
- обработку ошибок по каждому маркетплейсу;
- защиту от одновременных проверок одного товара;
- безопасное восстановление расписания после перезапуска.

## 7. Логика уведомлений

Уведомление отправляется только при переходе товара в состояние, когда его цена стала строго ниже порога.

Пример для порога 400 ₽:

- 420 ₽ — уведомление не отправлять;
- 400 ₽ — уведомление не отправлять;
- 399 ₽ — отправить уведомление;
- 380 ₽ — повторное уведомление не отправлять;
- 410 ₽ — сбросить состояние условия;
- 390 ₽ — отправить новое уведомление.

Если при первой успешной проверке цена уже ниже порога, отправить уведомление сразу.

Ошибки получения цены, временная недоступность страницы и отсутствие данных не должны сбрасывать состояние условия уведомления.

Изменение порога должно обрабатываться отдельно и не должно случайно вызывать массовую отправку уведомлений. Правила пересчёта состояния должны быть определены и протестированы.

### Защита от дубликатов

- Для одного перехода ниже порога должно создаваться не более одного логического уведомления.
- Если Telegram временно недоступен, уведомление должно попадать в очередь на повторную отправку.
- Повторная обработка задания не должна создавать дубликаты уведомления.
- Состояние и идентификатор уведомления должны сохраняться в базе данных.
- После перезапуска бот должен продолжить обработку очереди.

## 8. Формат уведомлений

Все уведомления отправляются в настроенную Telegram-группу.

Пример сообщения:

**🔻 Цена ниже порога!**

🎨 Название товара

🏪 Маркетплейс: Wildberries  
🔢 Артикул: 123456789  
💰 Текущая цена: 389 ₽  
🎯 Порог: 400 ₽  
📉 Изменение: −31 ₽, если предыдущая достоверная цена известна  
🏷 Тег: `#arton`

🔗 Открыть товар

Ссылка должна вести на конкретную карточку товара.

Если предыдущая цена неизвестна, не рассчитывать изменение. Если актуальная цена не подтверждена, уведомление о снижении не отправлять.

Все денежные значения отображать в российских рублях. Не смешивать валюты и не выполнять скрытую конвертацию.

## 9. Telegram-группа уведомлений

Группа используется исключительно для получения уведомлений о ценах.

В группе бот не должен:

- добавлять товары;
- изменять настройки;
- редактировать теги и пороги;
- принимать команды управления;
- использовать сообщения участников как инструкции.

Все операции управления доступны только владельцу в личном чате с ботом.

Владелец должен иметь возможность указать ID группы через личный чат.

### Кнопка «🔌 Проверить связь и доступ»

При нажатии выполнить фактическую диагностику и показать:

- доступность Telegram API;
- корректность настроенного ID группы;
- присутствие бота в группе;
- доступность необходимых прав отправки сообщений;
- состояние процесса мониторинга;
- время последней успешной проверки товаров;
- время последней попытки проверки;
- статус каждого маркетплейса;
- количество активных товаров;
- количество товаров с ошибками;
- количество ожидающих отправки уведомлений.

Не показывать успешный результат, если соответствующая проверка не выполнялась или завершилась ошибкой.

### Кнопка «📨 Проверить отправку в группу»

1. При нажатии немедленно отправить тестовое сообщение в настроенную группу, без дополнительного подтверждения.
2. После фактической попытки показать владельцу реальный результат.
3. При ошибке объяснить её причину и предложить действия для исправления.
4. Если группа не настроена, сообщить, как её подключить.
5. Тестовая отправка не должна менять историю цен, состояние пороговых условий или историю уведомлений.

## 10. Интерфейс управления

Главное меню личного чата:

- ➕ Добавить товар
- 📋 Список товаров
- 🏷 Теги и пороги
- 📈 История цен
- 🔌 Диагностика
- 📨 Проверить отправку в группу
- ⚙️ Настройки
- ❓ Помощь

### Список товаров

Для каждого товара отображать:

- название;
- маркетплейс;
- артикул;
- последнюю достоверную цену;
- тег;
- порог;
- время последней успешной проверки;
- статус мониторинга.

Предусмотреть постраничный вывод, фильтрацию по маркетплейсу, тегу и статусу.

### История цен

Показывать изменения цены по конкретному товару с датами и временем. Отдельно показывать ошибки проверок, чтобы они не воспринимались как изменение цены.

### Команды

- `/start` — запуск бота;
- `/help` — помощь;
- `/cancel` — отмена текущего сценария;
- `/list` — список товаров;
- `/tags` — список тегов и порогов;
- `/tagitems` — товары по выбранному тегу;
- `/status` — состояние мониторинга;
- `/check` — запрос внеплановой проверки с учётом ограничений площадки;
- `/setgroup` — настройка группы уведомлений;
- `/settings` — настройки.

Команды управления должны работать только в личном чате и только для владельца.

## 11. Безопасность

- Telegram ID владельца хранить в конфигурации.
- Проверять права доступа на серверной стороне для каждого обработчика и callback-кнопки.
- Не полагаться только на скрытие кнопок в интерфейсе.
- Хранить токен Telegram-бота в `.env` или другом защищённом хранилище.
- Не включать токены, пароли и другие секреты в исходный код и логи.
- Ограничить права доступа к конфигурационным файлам.
- Использовать безопасную обработку входных ссылок и артикулов.
- Предусмотреть защиту от повторной обработки одинаковых запросов.
- Не допускать параллельных задач, приводящих к повторным уведомлениям.

## 12. Технологический стек

Целевая операционная система — Ubuntu Server 24.04 LTS.

Предпочтительные технологии:

- Python 3;
- aiogram 3;
- SQLAlchemy;
- Alembic;
- SQLite на начальном этапе;
- APScheduler или другой подходящий планировщик;
- Pydantic;
- pytest.

Не добавлять Docker, Redis и другие дополнительные сервисы без обоснованной необходимости.

Реализовать модульную архитектуру, например:

- `bot/` — обработчики Telegram и клавиатуры;
- `services/` — бизнес-логика;
- `marketplaces/` — адаптеры маркетплейсов;
- `database/` — модели, миграции и репозитории;
- `scheduler/` — планировщик проверок;
- `config/` — конфигурация;
- `tests/` — автоматические тесты;
- `scripts/` — установка, диагностика и резервное копирование;
- `systemd/` — системная служба.

Для каждого маркетплейса использовать отдельный адаптер с единым интерфейсом. Способ получения данных может различаться в зависимости от площадки.

## 13. Структура базы данных

Минимально предусмотреть таблицы:

- `products` — товары;
- `price_history` — достоверные изменения цен;
- `check_logs` — результаты проверок;
- `tags` — теги и пороги;
- `notification_state` — состояние условий уведомлений;
- `notification_queue` — очередь уведомлений и результаты отправки;
- `settings` — настройки владельца и группы.

Хранить артикул, маркетплейс, прямую ссылку, название, тег, порог, последнюю цену, время проверки и служебные данные.

Дубликаты определять с учётом маркетплейса и идентификатора конкретной карточки. Одинаковые артикулы на разных площадках не считать одним товаром.

Использовать транзакции, индексы и миграции. Обеспечить согласованное резервное копирование SQLite во время работы бота.

## 17. Критерии готовности проекта

Проект считается готовым, если:

- владелец может добавить товар по ссылке или артикулу;
- при добавлении по артикулу можно выбрать маркетплейс;
- бот показывает найденную карточку и запрашивает подтверждение;
- работает пакетное добавление ссылок;
- теги автоматически устанавливают правильные пороги;
- бот получает фактические цены подходящими методами, а не из заглушек;
- расписание проверок соблюдает ограничения конкретных площадок;
- уведомления отправляются при правильном переходе через порог;
- повторные уведомления не дублируются;
- группа используется только для уведомлений;
- диагностика и тестовая отправка показывают фактический результат;
- база, планировщик и состояние уведомлений переживают перезапуск;
- ошибки получения данных не превращаются в ложные цены и уведомления;
- проект устанавливается и обслуживается по документации.
