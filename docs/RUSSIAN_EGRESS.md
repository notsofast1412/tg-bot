# Выход WB и Ozon через российский WireGuard

Владелец уточнил: сервер бота расположен в Европе и теперь разрешил настройку
VPN на нём для WB/Ozon. Предыдущее условие «не настраивать WireGuard на сервере»
заменено этим указанием. В облачном контейнере Codex VPN-клиент не устанавливается.

Цель — направить только HTTP-клиенты Wildberries и Ozon через российский выход.
SSH, Telegram и Яндекс сохраняют существующий маршрут. Смена общего default route
на рабочем сервере ради этой задачи не требуется. Доменные сервисы с динамическими
адресами не следует маршрутизировать по случайному списку IP карточек.

**Полученное уточнение:** доступен только готовый WireGuard-профиль сервиса;
российский Endpoint — `95.161.4.67`, SSH к нему нет. Выбран вариант с изолированным
namespace на европейском Ubuntu. Подготовлены код и
[пошаговые команды](WIREGUARD_PROFILE_SETUP.md); подключение ещё не выполнено.

## Уже подготовлено в приложении

`WB_PROXY_URL` и `OZON_PROXY_URL` — независимые необязательные SecretStr-настройки.
Им можно задать один и тот же доступный через WireGuard HTTP(S)-прокси. Пример
формата с условным приватным адресом (это не готовый адрес владельца):

```dotenv
WB_PROXY_URL=http://10.99.0.1:3128
OZON_PROXY_URL=http://10.99.0.1:3128
```

Реальные значения задаются защищённо в `.env`, права 600. Не заменяйте общий
`HTTPS_PROXY`: иначе изменится и маршрут Telegram. Короткие ссылки Ozon тоже
раскрываются через его прокси. При ошибке настроенного прокси нет автоматического
возврата к прямому соединению; цена остаётся неподтверждённой. Пустое значение
означает прежний маршрут, а не гарантированный российский выход.

## Если российский узел принадлежит владельцу и доступен по SSH

Предпочтительная схема:

1. Проверить существующие интерфейсы, маршруты, правила firewall и WireGuard
   на обоих узлах. Сохранить действующую конфигурацию перед изменениями.
2. Создать отдельный WireGuard peer или использовать явно предназначенный для
   приложения существующий peer. На европейском узле AllowedIPs должен включать
   только внутренний адрес российского шлюза; не добавлять 0.0.0.0/0 или ::/0
   в сетевое пространство, где работает SSH.
3. На российском узле поставить небольшой HTTP CONNECT proxy, например Squid,
   привязанный только к приватному WireGuard-адресу. Разрешить только приватный IP
   европейского peer, CONNECT на 443 и назначения `card.wb.ru`,
   `www.wildberries.ru`, `ozon.ru`, `www.ozon.ru`; остальные запросы запретить.
   Не открывать proxy-порт на публичном интерфейсе. Не использовать TLS interception.
4. Proxy отправляет запросы через обычный российский WAN своего сервера, ответы
   возвращаются в туннель. Для локального proxy не требуется перенаправлять весь
   транзитный трафик клиента через IP forwarding/NAT на российском узле.
5. В боте выставить оба proxy URL на приватный адрес шлюза, проверить фактические
   ответы площадок, Telegram и сохранение SSH, затем настроить восстановление
   WireGuard/proxy после перезагрузки.

Точные адреса, имя интерфейса, порт, подсеть и доступные firewall-инструменты
выбираются после инспекции серверов. Это схема установки, не утверждение, что
туннель уже создан. Приватные ключи генерируются/хранятся на сервере или вводятся
через защищённый канал; не пересылаются в чат и не включаются в архив проекта.

## Если доступен только готовый профиль VPN-сервиса

Такой профиль сам по себе не предоставляет HTTP-прокси на российском peer.
Подставлять его Endpoint в WB_PROXY_URL/OZON_PROXY_URL нельзя: это UDP WireGuard,
а не HTTP CONNECT.

В этом случае подходящая схема — отдельное Linux network namespace на европейском
сервере с WireGuard и небольшим HTTP-прокси внутри. Оба клиента бота используют
этот прокси через приватный veth-адрес; default route namespace идёт через VPN,
основной namespace/SSH/Telegram остаются на обычном маршруте. Нужны root/CAP_NET_ADMIN,
действующий профиль, DNS внутри namespace, отсутствие конфликтов приватных подсетей
и проверка, что при падении туннеля нет прямого выхода. Конкретная конфигурация
готовится только после определения типа профиля и осмотра сервера.

## Что нужно для продолжения

- Уточнить, есть ли SSH/root к российскому узлу или только готовый профиль.
- Получить публичный IP/домен российского Endpoint и порт (без приватных ключей).
- Предоставить профиль и SSH-аутентификацию только через защищённую конфигурацию.
  Доступ к европейскому серверу из этой облачной среды пока не установлен;
  выполняемые владельцем локальные SSH-команды остаются рабочим путём установки.

После настройки выполняется `python -m scripts.verify_server` и отдельный тест
отправки Telegram. Сравниваются точные товары, выбранные варианты и условия цены.
403, CAPTCHA и ограничения авторизации не обходятся; российский выход не гарантирует
доступность маркетплейсов. Фактических проверок с российским выходом пока не было.
